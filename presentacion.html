Flujo detallado — Login

De “Entrar” a sessionStorage

1
fetch() desde dashboard.js
POST /api/auth/login con { email, password } en el body JSON. Sin recargar la pagina.
2
AuthControlador recibe el JSON
@RequestBody LoginRequest deserializa el JSON y delega al AuthServicio.
3
BCrypt verifica la contrasena
encoder.matches(rawPassword, hashMySQL). La contrasena nunca se guarda en texto plano.
4
Respuesta JSON y sessionStorage
El servidor devuelve { usuarioId, nombre, rol }. El JS lo guarda en sessionStorage y redirige al dashboard.
// AuthControlador.java
@PostMapping("/api/auth/login")
public ResponseEntity<?> login(
        @RequestBody LoginRequest req) {
    try {
        Usuario u = authServicio
            .autenticarUsuario(req);

        Map<String,String> json = new HashMap<>();
        json.put("usuarioId", String.valueOf(u.getId()));
        json.put("nombre",    u.getNombre());
        json.put("rol",       u.getRol());

        return ResponseEntity.ok(json);

    } catch (RuntimeException e) {
        if ("ERR_NOT_FOUND".equals(e.getMessage()))
            return ResponseEntity.status(401)
                .body("Usuario no encontrado.");
        if ("ERR_BAD_PASSWORD".equals(e.getMessage()))
            return ResponseEntity.status(401)
                .body("Contrasena incorrecta.");
        return ResponseEntity.status(500)
                .body("Error interno.");
    }
}

Codigo real del proyecto

ticketpro.sql

CREATE DATABASE IF NOT EXISTS ticketpro;
USE ticketpro;

-- 1. USUARIOS (email unico, contrasena siempre hasheada)
CREATE TABLE IF NOT EXISTS usuarios (
  id       INT NOT NULL AUTO_INCREMENT,
  nombre   VARCHAR(100) COLLATE utf8mb4_unicode_ci NOT NULL,
  email    VARCHAR(100) COLLATE utf8mb4_unicode_ci NOT NULL,
  password VARCHAR(255) COLLATE utf8mb4_unicode_ci NOT NULL,
  rol      VARCHAR(20)  COLLATE utf8mb4_unicode_ci NOT NULL DEFAULT 'cliente',
  PRIMARY KEY (id),
  UNIQUE KEY email (email)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

-- 2. INCIDENCIAS (tres FK, dos politicas de borrado distintas)
CREATE TABLE IF NOT EXISTS incidencias (
  id             INT NOT NULL AUTO_INCREMENT,
  titulo         VARCHAR(100) NOT NULL,
  descripcion    TEXT         NOT NULL,
  estado         VARCHAR(20)  NOT NULL DEFAULT 'Pendiente',
  fecha_creacion TIMESTAMP    DEFAULT CURRENT_TIMESTAMP,
  categoria_id   INT DEFAULT NULL,
  cliente_id     INT DEFAULT NULL,
  informatico_id INT DEFAULT NULL,
  PRIMARY KEY (id),
  CONSTRAINT incidencias_ibfk_1
    FOREIGN KEY (categoria_id)   REFERENCES categorias (id) ON DELETE SET NULL,
  CONSTRAINT incidencias_ibfk_2
    FOREIGN KEY (cliente_id)     REFERENCES usuarios (id)   ON DELETE CASCADE,
  CONSTRAINT incidencias_ibfk_3
    FOREIGN KEY (informatico_id) REFERENCES usuarios (id)   ON DELETE SET NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

Por que ddl-auto=update

Con create o create-drop cada reinicio del contenedor borraria todas las tablas. Con update, Hibernate solo aplica diferencias. Los datos sobreviven siempre.

Variables de entorno

Las credenciales viajan en el fichero .env (no commiteado al repositorio). Spring Boot las lee como ${DB_HOST}, ${MYSQL_ROOT_PASSWORD}.

Volume persistente

volumen_datos_mysql asegura que los datos de MySQL sobreviven aunque se detenga o recree el contenedor en AWS EC2. El script 01-ticketpro.sql solo se ejecuta la primera vez.

Seguridad en produccion

HTTPS con Let's Encrypt y Certbot

1
Instalar Certbot y su extension para Nginx
Via SSH a la maquina EC2 de Amazon, instalamos las herramientas necesarias:
sudo apt update
sudo apt install certbot python3-certbot-nginx -y
2
El comando definitivo
Certbot habla con Let's Encrypt, demuestra que somos los duenos del dominio, genera las claves criptograficas y modifica la configuracion de Nginx para activar el puerto 443:
sudo certbot --nginx -d ticketpro.yatat.es
3
Reiniciar Nginx para aplicar los cambios
Por si acaso, reiniciamos el servidor web del host para asegurar el tiro:
sudo systemctl restart nginx

Que hace Certbot al ejecutarse

  • — Pide un correo para avisar si el certificado caduca.
  • — Solicita aceptar los terminos de servicio de Let's Encrypt.
  • — Pregunta si redirigir HTTP a HTTPS. Respondimos SI: quien intente entrar por http:// es redirigido automaticamente a https://.

Resultado

La aplicacion queda accesible en https://ticketpro.yatat.es con certificado valido firmado por Let's Encrypt, renovacion automatica incluida, y todo el trafico HTTP redirigido a HTTPS por Nginx.

Por que Let's Encrypt y no un certificado de pago

Let's Encrypt es una CA publica gratuita reconocida por todos los navegadores. Para un proyecto de produccion real, ofrece exactamente la misma seguridad TLS que un certificado comercial.

Testing y Madurez

Gestion Inteligente de Errores (Fallback)

El manejo de excepciones no depende solo del backend. Se diseno una vista error.html con redireccion adaptativa.

El problema resuelto

Normalmente, si un usuario entra a una ruta 404, el boton estatico de "Volver" lo manda al Login, destruyendo su sesion actual y rompiendo la experiencia de usuario (UX).

Enrutamiento Inteligente

Si se intenta acceder a una ruta inexistente (ej. /probando), salta el error 404. Al hacer clic en "Volver", el sistema evalúa: si hay sesión activa va al Dashboard; si no, al Login.

// error.html — Fallback dinamico UX
document.getElementById('btnAcceso')
  .addEventListener('click', function () {
    
    // El frontend verifica su propio estado
    var id = sessionStorage.getItem('usuarioId');
    
    if (id) {
        // La sesion esta viva
        window.location.href = '/dashboard.html';
    } else {
        // No hay sesion o ha caducado
        window.location.href = '/login';
    }
});

Esta resolucion demuestra que el sistema tiene una tolerancia a fallos robusta de extremo a extremo, protegiendo la sesion del usuario final en produccion.

Honestidad tecnica

Limitaciones conocidas — y el siguiente paso

Fase 1 — Acotacion de alcance

La API no tiene filtros globales de Spring Security. Un usuario que conozca la URL puede hacer peticiones sin token desde Postman.

GET /api/usuarios devuelve el hash BCrypt en el JSON. Irreversible, pero innecesario.

Fase 2 — Hoja de ruta

JWT: Al hacer login el servidor emite un token firmado. Cada peticion lo envia en Authorization: Bearer <token>. Sin token valido: 401 automatico.

Spring Security: Un OncePerRequestFilter interceptara todas las rutas /api/** antes de que lleguen al controlador.

La arquitectura REST + frontend desacoplado esta disenada para anadir estas capas sin refactorizar el nucleo. Es una decision de acotacion, no un olvido.
